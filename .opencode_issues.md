# Open issues found in this loop

## 1. A one-sided cost check certifies a sweep comparison without both ratios

- File: `scripts/train_llama_depth_sweep.py` (`compare_sweep_cells`)
- `cost_matched_within_25pct` is computed from whichever of the params/FLOPs
  ratios are present, and `None` is only returned when both are missing. A
  legacy/incomplete cell with, say, a params ratio of 1.0 but no FLOPs value
  therefore reports `cost_matched_within_25pct=True` and becomes
  `certifiable`, even though the compute-matched premise is only half
  verified.
- Confirmed with a synthetic cell: candidate params ratio 1.0, candidate FLOPs
  missing, reference has both; the row reports `True`, `certifiable=True`,
  `p_one_sided=0.0`, and `beats_reference_significantly=True`.
- The comparison's own labels say "the params/FLOPs ratios are unavailable"
  only when `None`, and the sweep contract treats both dimensions as part of
  the premise, so a partial ratio must not be read as a match.
- Fix: set `cost_matched_within_25pct` only when both ratios exist; leave it
  `None` (unavailable) when either is missing.

## 2. Ablation curve diagnosis stops one window before the reported weights

- File: `scripts/ablation.py` (`run_one`)
- Curve points are collected only when `(step + 1) % curve_every == 0`. When
  `max_steps` is not divisible by `curve_every` (e.g. the auto period
  `max_steps // 5` for `max_steps=3`), the final step never gets a curve point,
  so `curve_diagnosis`/`curve_classification` describe weights from an earlier
  step while `final_loss`/`val_loss` describe the final weights.
- Reproduced by running a tiny row with `max_steps=3, curve_every=2`: the run
  reports `curve_steps=[2]`, while `final_loss` is from step 3.
- The MoE trainer already handles this explicitly (`step + 1 == max_steps`
  forces a final point), and its comment states why the diagnosis must land on
  the reported weights.
- Fix: include `step + 1 == max_steps` in the ablation curve trigger.

## 3. MoE dataset curve samples overlap the final validation prefix after a wrap

- File: `scripts/train_moe_tiny.py` (`run_one`, `next_curve_batch`)
- Dataset mode skips the first `--val-batches` validation windows only when the
  curve loader is first opened. When the curve iterator is exhausted, the
  restart path only calls `iter(curve_loader)` and does not skip the prefix
  again; the initial skip also resets and breaks on `StopIteration`, then draws
  from the prefix it was supposed to avoid.
- Reproduced with a fake validation loader of 3 batches, `val_batches=2`,
  `curve_batches=2`, `max_steps=4`: curve points consumed batch 2 then wrapped
  to batch 0, and the final validation pass consumed batches 0 and 1, so the
  "disjoint" curve and final estimate shared samples.
- Fix: skip the final-validation prefix on every pass through the curve loader
  and fail clearly if the split has no batches left after that prefix.

## 4. Seed aggregation loses the requested seed list when given a generator

- Files: `scripts/train_gpt2.py` (`aggregate_seed_runs`),
  `scripts/train_llama_depth_sweep.py` (`aggregate_sweep_cell`)
- Both functions iterate `seeds` and later call `len(list(seeds))` (GPT) or
  rebuild `seed_list = [int(s) for s in seeds]` (sweep). A one-shot iterable
  is exhausted by the per-seed loop, so the returned `seeds` list is empty and
  `n_seeds_requested` is 0 even though `per_seed` contains every requested
  seed.
- Reproduced with `iter([42, 43])`: GPT aggregation returned
  `seeds=[]`, `n_seeds_requested=0`, `per_seed=2`; the sweep returned the same
  empty list, making completeness/coverage checks divide by zero or report a
  false request count.
- Fix: materialize and normalize `seeds` once at function entry and use that
  list for both the per-seed loop and the returned metadata.
