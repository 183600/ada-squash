# Open issues found in this loop

## 1. `_seed_means` fabricates per-seed pairs for a multi-seed aggregate without `per_seed`

- File: `scripts/ablation.py` (`_seed_means`, `_paired_row_test`, `baseline_comparison`)
- Confirmed with synthetic input: a row shaped like a legacy aggregate
  (`seeds=[42,43,44]`, pooled `val_loss=2.0`, no `per_seed`) is treated as
  three independent seed observations all equal to 2.0. Pairing it against a
  reference with the same three seeds produces `p_one_sided=0.0` and
  `beats_reference_significantly=True`, with zero variance invented by the
  fallback.
- The normal summary writer (`aggregate_seed_summaries`) always writes
  `per_seed`, so current runs do not produce this shape. The function contract
  is still wrong: its docstring says the fallback is for a *single-run*
  summary, and a hand-written/older/external summary can turn a pooled mean
  into false significance instead of an unpaired row.
- Fix: only apply the no-`per_seed` fallback when the row names exactly one
  seed. A multi-seed row without per-seed losses has no pairing basis.

## 2. `resolve_dataset_revision` never resolves an explicitly requested revision

- File: `scripts/data_pipeline.py` (`resolve_dataset_revision`)
- The docstring promises to resolve the requested dataset revision to the
  concrete upstream commit and says the resolved hash keys the materialized
  cache, so a moved branch cannot silently reuse a stale held-out cache. The
  implementation returns any truthy `revision` unchanged, before contacting
  the Hub.
- A run pinned to a mutable branch/tag therefore records the branch name as
  `dataset_revision_resolved`; after the branch moves, the cache key is still
  identical and the held-out cache can silently serve documents from the old
  commit while the training stream loads the new one.
- Fix: resolve explicit revisions through `HfApi.dataset_info(..., revision=...)`
  too, cache per (dataset, revision), and fall back to the requested value only
  when the Hub lookup fails.

## 3. `triage_nonfinite` ignores non-finite fp32 logits when the loss is finite

- File: `adasquash/diagnostics.py` (`triage_nonfinite`, `classify_nan_stage`)
- Stage 2 records `fp32_logits_finite` and the first non-finite module outputs,
  but `stage2_bad` and `classify_nan_stage` only checked the fp32 *loss* (and
  the loss denominator / forward exception). A model whose logits are NaN/Inf
  only at `ignore_index` target positions - the shifted last target is always
  ignored, so a softmax/division pathology in the final position is enough -
  has a finite cross-entropy mean: the ignored rows are excluded from the
  reduction. The evidence carries `fp32_logits_finite: False` (and the
  offending module) yet stages 3-4 still run and the verdict is
  `unreproduced`, sending the reader to "transient/hardware" instead of the
  fp32 math stage.
- Confirmed with a toy model that returns NaN logits at the target-ignored
  last position and a finite loss: `triage_nonfinite` returned
  `stage='unreproduced'` with `fp32_logits_finite=False`.
- Fix: treat `fp32_logits_finite is False` (and any non-finite module output
  named by `first_nonfinite_modules`) as a stage-2 `fp32_math` failure in both
  `stage2_bad` and `classify_nan_stage`, so the diagnosis says fp32 math and
  stages 3-4 are recorded as skipped.

## 4. `classify_nan_stage` ignores an autocast forward that raised

- File: `adasquash/diagnostics.py` (`classify_nan_stage`, `triage_nonfinite`)
- Stage 3 records `autocast_error` when the autocast forward raises, but the
  classifier only checks `autocast_forward_finite is False` (the overflow
  case). With an error the key stays `None`, so the verdict falls through to
  `gradients`/`unreproduced` with no note that the low-precision forward was
  the stage that failed. This is the same positive-evidence asymmetry that
  `forward_error` already handles for stage 2: an exception in the stage is
  evidence about that stage.
- Confirmed with a model whose forward raises only under autocast (and with a
  direct `classify_nan_stage({'autocast_error': ...})` call): the verdict was
  `unreproduced` even though `autocast_error` was set.
- Fix: classify `autocast_error` as `mixed_precision` and put the exception in
  the diagnosis text, next to the existing overflow wording.

## 5. Checkpoints record the mutable dataset/tokenizer revision, so resume can silently change data

- File: `scripts/train_gpt2.py` (train setup; `_DATA_ARGS` / `restore_data_args`)
- The data pipeline resolves the requested dataset/tokenizer revisions to
  concrete upstream commit hashes (`dataset_revision_resolved` /
  `tokenizer_revision_resolved` in the split report) and keys the held-out
  cache on the resolved hash. But the resolved value never reached `args`,
  and checkpoints save `vars(args)`; a run started on the default branch or a
  moving tag therefore stored `dataset_revision=None`/`main` in its
  checkpoints. `restore_data_args`, whose comment states the revisions are the
  data *version* that must not change across a resume, restored that raw
  string, and the resumed run resolved it to whatever upstream commit is
  current then - continuing on different documents under the same manifest.
  The tokenizer revision had the same hole.
- Fix: once the train split is open, replace `args.dataset_revision` /
  `args.tokenizer_revision` with the report's resolved commits when available,
  so every checkpoint (and the run manifest) records the actual data version
  and a resume pins it. With the default branch moved, the resumed loader
  still opens the checkpoint's commit instead of the new head.
